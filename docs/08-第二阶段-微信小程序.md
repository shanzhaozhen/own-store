# 08 · 第二阶段：微信小程序自助打印

> **v1 不实现。**这份文档只锁定架构方向，确保 v1 的代码不会挡住第二阶段的路。

## 目标流程

顾客不用再麻烦店里的人：

```
打开小程序 → 选文件（微信聊天文件 / 相册 / 手机文件）
   → 服务端转换 + 生成预览 → 顾客确认页数和效果
   → 显示价格 → 微信支付
   → 店铺打印机自动出纸 → 顾客到柜台取
```

## 三方架构

```
┌──────────────┐
│  微信小程序   │  选文件、预览、确认、支付、看排队进度
└──────┬───────┘
       │ HTTPS
┌──────▼──────────────────────────────┐
│  云服务端（FastAPI）                 │
│  · 文件接收与临时存储                │
│  · 调 core/ 做转换 + 增强 + 生成预览  │
│  · 计价、微信支付下单、支付回调       │
│  · 订单状态机、任务队列               │
└──────┬──────────────────────────────┘
       │ 服务端 → 店铺，长连接（WebSocket）下发任务
┌──────▼──────────────────────────────┐
│  店铺 Agent（跑在店铺那台 Win10 上）  │
│  · 直接 import shop_print.core       │
│  · convert → printing → history      │
│  · 上报打印结果与耗材/故障状态        │
└─────────────────────────────────────┘
```

**为什么用店铺主动发起的长连接，而不是服务端直连店铺机**：店铺是普通家用宽带，没有固定 IP，也**绝对不应该把店铺电脑暴露到公网**。Agent 主动向云端建立 WebSocket 出站连接，云端只在这条连接上下发任务。店铺侧不开任何入站端口。

## v1 已经为此做的两件事

1. **`core/` 不 import 任何 Qt** —— Agent 和服务端都在无图形界面的进程里跑，能原样复用增强、转换、打印逻辑。这条规则写进了 `CLAUDE.md`，是硬约束。
2. **打印记录从第一天就落 SQLite** —— `history.db` 的表结构里已经留了金额字段。第二阶段的收费统计、对账直接用这张表。

桌面工具和 Agent 可以共存：桌面工具管柜台来的顾客，Agent 管小程序订单，两边写同一个 `history.db`。

## 计价

按页数 × 单价，区分：单/双面、纸张（A4/A3）、是否需要增强处理。

**页数必须由服务端转换后的 PDF 实际页数决定，不能信客户端传的数字。**计价和页数校验都在服务端做，支付金额由服务端生成订单时确定。

## 需要提前准备的资质（非技术，但会卡进度）

- 小程序账号：个人主体**不能开通微信支付**，需要个体工商户或企业主体
- 微信支付商户号（需要营业执照、对公或经营者账户）
- 小程序类目：涉及文件上传打印，可能需要相关类目资质
- 服务器 + 备案域名（小程序只能请求 HTTPS 且域名要在白名单里）

这一块建议在动手写代码之前先确认能不能办下来。

## 安全与隐私边界

顾客的文件可能是身份证、合同、成绩单，非常敏感。

- **顾客文件不做长期云端存储**：打印完成后按短时限（如 2 小时）自动删除，只留订单元数据
- 传输全程 HTTPS；对象存储用一次性签名 URL，不可枚举
- 预览图也是临时文件，同样限时删除
- Agent 与云端之间用设备密钥认证，密钥不硬编码在打包产物里
- **打印前保留人工确认开关**：默认自动打印，但店里可以切成"需要柜台确认"模式，防止恶意刷单浪费纸墨
- 单笔页数上限 + 单账号频次限制，防滥用
- 日志里不记录文件内容，只记文件名 hash 和页数
