# 02 · 架构与分层

## 一句话

**一切文件先归一化成 PDF，再统一预览、统一打印。**图片在归一化之前多走一道"去底增强"。

这样做的好处：预览器只需要认 PDF 一种格式；打印路径只有一条，不用为每种文件类型各写一套打印逻辑；顾客看到的预览和打出来的纸是同一份数据。

## 分层

```
┌─────────────────────────────────────────────────┐
│  ui/          PySide6，只做展示与调度            │
│  main_window / page_photo / page_ocr            │
│  page_cards / page_inbox / page_print           │
│  widgets / style.qss / workers.py               │
└────────────────────┬────────────────────────────┘
                     │ 只调用 core 的函数，不写算法
┌────────────────────▼────────────────────────────┐
│  core/        纯逻辑，不 import 任何 Qt          │
│                                                 │
│  intake.py   文件从哪来（微信目录/待打印目录/     │
│              剪贴板/拖拽）                        │
│  enhance.py  图片去底增强                        │
│  convert.py  任意文件 → PDF                      │
│  cards.py    证件二合一（按实物尺寸拼一张纸）      │
│  printing.py PDF → 打印机 + 打印预览              │
│  ocr.py      图片 → 文字 + 版面 → docx/txt        │
│  history.py  打印记录（SQLite）                  │
└─────────────────────────────────────────────────┘
   texts.py（全部中文文案）  paths.py（全部路径）
   config.py（%LOCALAPPDATA%\ShopPrint\config.json）
   self_check.py（--self-check 自检报告，不开界面，见 docs/07）
```

**`core/` 不许 import Qt** —— 这条规则是为第二阶段服务的：小程序的服务端 / 店铺 Agent 要在没有图形界面的进程里调用同样的增强、转换、打印逻辑。任何一处混进 `PySide6`，第二阶段就得重写。

`__main__.py` 里有两个**必须在建 QApplication 之前**处理掉的分支：`--office-worker`（Office 转换子进程重新执行自己）和 `--self-check`（打包后的排障入口）。两者都不需要界面，先处理掉才不会多开一个窗口。

## 数据流

### 打印一份文档

```
文件（拖入 / 微信目录 / 待打印目录 / 剪贴板）
   ↓ intake.py 归一成 SourceFile（路径 + 类型 + 缩略图）
   ↓ convert.py
   ├─ 图片 → enhance.py 增强 → 排到 A4 页 → PDF
   ├─ doc/docx → Word COM（子进程）→ PDF
   ├─ xls/xlsx → Excel COM（子进程，先设"一页宽"）→ PDF
   ├─ txt → PyMuPDF 排版（内嵌中文字体）→ PDF
   └─ pdf → 原样（校验可读性 / 加密提示）
   ↓ 缓存到 %LOCALAPPDATA%\ShopPrint\cache\<源文件hash>.pdf
   ↓ printing.preview_sheet()：画整张纸给长辈看（内容摆在哪、会不会被缩、
   ↓                          四周打不到的边在哪）—— 和真打印同一套算式
   ↓ printing.print_pdf()：DEVMODE（份数/双面/纸张/单色）+ GDI 逐页送图
   ↓ history.py 落一条记录
柯美 225i 出纸
```

**首页没有「打印文档」入口**（原件是 Office 文档时直接在 Office 里打更省事），但这条链路是所有活儿的统一出口：照片变清楚、证件二合一、微信收到的文件、拖进来的文件，最后都汇到打印预览页。

### 照片转文字文档

```
图片 → enhance.py（裁正 + 去阴影，输出灰度图）
     ↓ 这一步和"增强打印"共用，不重复实现
     ↓ ocr.py：RapidOCR → [(box, text, score)]
     ↓ 版面重建：行聚类 → 段落切分 → 标题/居中判定
     └→ python-docx 生成 .docx，同时另存 .txt
```

注意 **OCR 的输入是增强后的图**，不是原始照片。去阴影 + 透视校正之后识别率明显更高，两个功能共用同一条前处理链是有意设计。

## 耗时操作一律离开 UI 线程

| 操作 | 在哪跑 | 为什么 |
|---|---|---|
| 全分辨率图像增强 | `QThreadPool` 工作线程 | 千万像素图要一两秒 |
| OCR | `QThreadPool` 工作线程 | 弱 CPU 上一页可能要好几秒 |
| Office COM 转换 | **独立子进程** | Word/Excel 会卡死甚至崩溃，不能拖死主程序 |
| 打印光栅化与送数据 | `QThreadPool` 工作线程 | 多页 PDF 逐页渲染 |
| 打印预览 | `QThreadPool` 工作线程 | 要问驱动、要渲染整页 |
| **读一张照片** | `QThreadPool` 工作线程 | 手机照片十几兆，解码就要一秒 |
| **粘贴图片（存盘）** | `QThreadPool` 工作线程 | PNG 编码一张大图要一两秒 |
| **扫监控目录** | `QThreadPool` 工作线程 | 微信目录可能上万个文件，`rglob` 很慢 |
| 目录监控 | `watchdog` 后台线程 | 事件通过信号发回 UI |

界面必须始终能响应，长辈看到"卡住不动"就会反复点或直接关掉。而且**卡住的样子很误导**：界面线程一被堵住，Windows 画的是一张定格的旧画面，还会随窗口缩放被拉伸 —— 用户报回来的原话是"按钮变形定格"，其实是没在后台跑活儿。

`ui/workers.py` 的 `run_async()` 有一处必须留着：它自己**持有 Worker 的强引用**直到任务跑完。Worker 一被垃圾回收，`signals` 跟着没了，连接断掉，回调再也不会到 —— 界面上表现为"点了没反应"，日志里什么都没有。回归测试在 `tests/test_workers.py`。

**预览用缩略图，打印用全分辨率。**增强页的滑块要实时出效果，所以预览统一把长边缩到 1000px 处理；真正打印或保存时才用原图跑一遍完整参数。

## 状态与配置放哪

```
%LOCALAPPDATA%\ShopPrint\
├── config.json     打印机名、默认份数、微信目录、增强默认模式、云端 OCR 配置
├── history.db      SQLite 打印记录
├── cache\          转换出来的 PDF（按源文件 hash 命名，定期清理）
├── logs\           轮转日志，技术细节只进这里
└── output\         OCR 生成的 docx / txt，增强后另存的图片
```

`C:\打印\待打印\` —— 面向长辈的"投递箱"，安装时创建并在桌面放快捷方式。

所有路径集中在 `paths.py`，不要在各处硬编码。

## 第二阶段怎么接

```
微信小程序 ──HTTPS──▶ 云服务端（订单 + 微信支付）
                          │
                          │ 长连接下发打印任务
                          ▼
                    店铺 Agent（跑在店铺机上）
                          │ 直接 import core/
                          ▼
                  convert → printing → history
```

Agent 复用现在的 `core/`，不需要 UI。桌面工具和 Agent 可以共存：桌面工具管柜台顾客，Agent 管小程序订单，两边写同一个 `history.db`。详见 [08-第二阶段-微信小程序](08-第二阶段-微信小程序.md)。
