# ADR-003 · 打印后端选择

- **日期**：2026-08-16
- **状态**：已采纳（保留可切换的备选）
- **决策**：默认用 pywin32 GDI 直接打印（PyMuPDF 光栅化 + `StretchDIBits`）；`print_backend` 配置项保留 `sumatra` 备选路径

## 背景

要把 PDF 打到店铺的柯美 bizhub 225i（只能黑白），且必须精确控制份数、单双面、纸张、方向、单色。长辈不会用打印机驱动的设置对话框，**所有参数必须由程序设好，不能弹任何系统对话框**。

## 考虑过的选项

### `ShellExecute(hwnd, "print", file, ...)` / 关联程序打印

最省事：交给系统默认 PDF 阅读器。

否决：拿不到任何控制权。份数、双面、纸张全按阅读器的默认值走，有些阅读器还会弹自己的打印对话框。而且店铺机装了什么 PDF 阅读器不受我们控制 —— 换个阅读器行为就变了。对长辈来说"有时候弹窗有时候不弹窗"是灾难。

### SumatraPDF 便携版命令行

```
SumatraPDF.exe -print-to "<打印机名>" -print-settings "1-5,duplex,2x" -silent -exit-when-done <file.pdf>
```

久经考验，驱动兼容性极好，是很多打印服务的标准做法。

不作为默认的理由：多一个外部 exe 依赖（GPLv3，随包分发要注意许可）；拿不到细粒度进度（没法显示"正在打印第 2 页 / 共 5 页"，而这个反馈对长辈很重要）；参数通过字符串传递，出错时只能从退出码猜。

**但保留为备选** —— 柯美驱动的真实行为在开发机上无法验证，万一 GDI 路径上页边距或双面出问题，切过去是最快的解法。

### GDI 直接打印（采纳）

```python
h = win32print.OpenPrinter(name)
dm = win32print.GetPrinter(h, 2)["pDevMode"]
dm.Copies, dm.Duplex, dm.PaperSize, dm.Color = ...  # 显式设死，包括单色
dc = win32ui.CreateDC()
dc.CreatePrinterDC(name)
for page in doc:
    pix = page.get_pixmap(dpi=300, colorspace=fitz.csGRAY)
    dc.StretchDIBits(...)  # 按可打印区域等比居中
```

优点：

- **DEVMODE 完全可控**，份数/双面/纸张/方向/单色都是显式设的，不靠驱动默认值
- **无外部依赖**，pywin32 已经在依赖里（Office COM 也要用）
- **逐页进度**天然可得，界面能显示"第几页 / 共几页"
- 任何有 Windows 驱动的打印机都能打，不挑型号

## 关键实现约束

| 约束 | 理由 |
|---|---|
| 光栅化用 **300 dpi** | 600 dpi 下 A4 灰度是 7016×9933 ≈ 70 MB/页，弱机器吃不消；300 dpi 对黑白文字足够，一页约 17 MB |
| 用 `PHYSICALOFFSETX/Y` + `HORZRES/VERTRES` 算**真实可打印区域** | 可打印区域 ≠ 纸张尺寸，不算的话内容会被裁掉边 |
| 页宽 > 页高时把 `dm.Orientation` 设横向 | 否则宽页被压扁 |
| `StartDoc/StartPage/EndPage/EndDoc` 严格配对，异常路径 `AbortDoc` | 否则打印队列里留一个卡死任务，长辈只能重启电脑 |
| `dm.Color` 显式设单色 | 225i 只有黑白，别让驱动做半调色的额外处理 |

## 未验证的部分（必须诚实标注）

开发机上**只有虚拟打印机**（`Adobe PDF`、`Microsoft Print to PDF`、`OneNote`）。柯美驱动的 DEVMODE 字段支持情况、纸张列表、双面器是否存在，都无法在这里验证。

开发期用 `Microsoft Print to PDF` 当替身跑通全链路；交付前**必须在店铺机上实打一次**（拍照文档、Word、Excel 宽表、多页 PDF、双面各一次）。

## 复查条件

若店铺机实测发现 GDI 路径的页边距、缩放或双面有问题，且短时间内定位不到原因，直接把 `print_backend` 切成 `sumatra`，同时在 `docs/04` 记下具体现象。别在现场跟驱动死磕 —— 店里等着做生意。
