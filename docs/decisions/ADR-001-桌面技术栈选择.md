# ADR-001 · 桌面技术栈选择

- **日期**：2026-08-16
- **状态**：已采纳
- **决策**：Python 3.14 + PySide6，PyInstaller `--onedir` 打包

## 背景

要做一个跑在店铺 Windows 10 台式机上的桌面工具，操作者是不熟悉电脑的长辈。核心工作量集中在三块能力：

1. 图像处理（拍照文档去阴影、透视校正、二值化）
2. 中文 OCR + 版面重建
3. Windows 打印控制（DEVMODE 里设份数/双面/纸张/单色）与 Office 文档转 PDF

## 考虑过的选项

### Electron + React + antd

项目发起人的主力技术栈（`C:\Project` 下有多个 antd 项目），界面开发最快。

但三块核心能力全都要往外借：图像处理要么内嵌 Python，要么用 sharp + 手写算法；OCR 要 `onnxruntime-node`；Windows 打印和 Office COM 在 Node 侧要么找不到成熟绑定，要么还是得起 Python 子进程。结果是**跨语言进程通信成为主要复杂度来源**，而这部分复杂度全在最容易出 bug 的地方。打包体积 300MB+ 起，长辈机器上 Chromium 启动也更慢。

### Python 核心 + 本地 Web UI（FastAPI + React）

核心逻辑在 Python，界面在浏览器。第二阶段小程序能直接复用后端接口，听起来很划算。

否决原因是**长辈要面对浏览器**：地址栏、书签栏、多标签、浏览器自己的打印对话框，全是干扰和误操作来源。还要额外处理开机自启、端口被占、浏览器默认程序被改。出问题时排查路径变长（是服务没起来？端口冲突？浏览器缓存？）—— 而现场没人能帮他们排查。

### Python + PySide6（采纳）

三块核心能力在同一个语言里，无胶水层：

- OpenCV + numpy 做图像处理，生态最成熟，算法调参直接
- RapidOCR + onnxruntime 做中文 OCR
- pywin32 直接调 `win32print` / `win32ui` 控制打印，`win32com` 调 Office COM
- PyMuPDF 一个库同时负责 PDF 生成、渲染预览、光栅化打印

界面是原生窗口：没有浏览器干扰，全屏大按钮好做，QSS 能满足"大字大按钮"的样式需求。

## 代价

- 发起人主写前端，Qt 的布局模型（`QVBoxLayout` / `QStackedWidget` / 尺寸策略）需要适应一下。缓解办法：`ui/widgets/` 里先封装好 `BigButton` / `BigCard` 这几个基础件，页面代码就只是拼装。
- 打包体积约 300–450 MB。拷一次就完事，可接受。
- PySide6 6.11 要求 Win10 1809+，店铺机版本需现场确认。

## 结果

第二阶段的复用靠**分层**而不是靠技术栈：`core/` 不 import 任何 Qt，服务端和店铺 Agent 可以原样 import。这条规则写进了 `CLAUDE.md`，是硬约束。
